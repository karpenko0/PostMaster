# SPEC-005. Ввод и валидация даты и времени

**Проект:** Telegram-бот «PostMaster»
**Этап:** MVP
**Версия:** 1.0
**Статус:** к разработке

> Рабочая структурированная редакция переданного ТЗ: требования и идентификаторы сохранены,
> повторяющиеся примеры и последовательности сокращены. Точные тексты ответов §26/27 сохранены.

---

# 1. Назначение

Обработка даты и времени публикации после отправки фотографии: принять текст, проверить формат, существование даты и времени, будущее локальное время пользователя и передать нормализованный результат дальше.

# 2. Цель

В `WAITING_DATETIME` принять сообщение, проверить формат и календарь, учесть timezone, проверить будущее время, передать результат дальше. При ошибке дать подсказку и не терять фотографию.

# 3. Scope

Текст в формате `ДД.ММ.ГГГГ ЧЧ:ММ`, строгий разбор, проверка календаря, времени и будущего момента в timezone пользователя; нормализация в UTC; передача данных следующему этапу; обработка ошибок и повторный запрос.

# 4. Out of Scope

Естественный язык («завтра в пять», «через два часа»), календарь, изменение timezone, запись `posts`, Scheduler, публикация, изменение и повторение публикаций. Детальные правила timezone — SPEC-006, создание публикации — SPEC-009.

# 5. Зависимости

SPEC-003 (FSM), SPEC-004 (фото), SPEC-006 (timezone); следующий этап — SPEC-009.

# 6. Предусловия

Пользователь существует; фото принято и хранится в FSM; состояние `WAITING_DATETIME`; timezone пользователя известен либо действует `DEFAULT_TIMEZONE`.

# 7. User Stories

- US-005-01: принять `07.10.2026 15:00`, если момент будущий.
- US-005-02: на «завтра в пять» дать сообщение §26 без потери фото.
- US-005-03: прошлое или текущее время не создаёт публикацию.
- US-005-04: после ошибки сохранить `WAITING_DATETIME`, повторная отправка фото не нужна.

# 8. Формат даты

`ДД.ММ.ГГГГ ЧЧ:ММ` = `%d.%m.%Y %H:%M`; пример `07.10.2026 15:00`.

# 9. Формальные требования к строке

`DD.MM.YYYY HH:MM`: двухзначные день, месяц, часы, минуты; четырёхзначный год; обязательны точки, один пробел и двоеточие.

# 10. Допустимые примеры

`07.10.2026 15:00`, `01.12.2026 09:30`, `31.12.2026 23:59`, `02.01.2027 00:01` — только если находятся в будущем.

# 11. Недопустимые примеры

`завтра`, `завтра в пять`, `7 октября`, `07/10/2026 15:00`, `2026-10-07 15:00`, `07.10.26 15:00`, `07.10.2026`, `15:00`, `07.10.2026 в 15:00`.

# 12. Валидация календарной даты

Отклонить `32.10.2026 15:00`, `31.11.2026 15:00`, `00.10.2026 15:00`, `15.13.2026 15:00`, `29.02.2026 15:00` (2026 не високосный).

# 13. Валидация времени

Диапазон `00:00`–`23:59`. Отклонить `24:00`, `25:30`, `12:60`, `-1:00`, `15:99`.

# 14. Строгий парсинг

Использовать `datetime.strptime(value, "%d.%m.%Y %H:%M")` и отклонять любое несоответствие формату.

# 15. Внутренний API-контракт

`parse_publication_datetime(value: str, timezone: str, now: datetime) -> ParsedPublicationDateTime`.

# 16. Входные параметры

`value` — строка пользователя; `timezone` — timezone пользователя; `now` — текущий момент для сравнения. Все обязательны.

# 17. Выходной DTO

`ParsedPublicationDateTime(local_datetime: datetime, timezone: str, utc_datetime: datetime)`; правила преобразования UTC уточняются в SPEC-006.

# 18. Результаты обработки

`VALID`: возвращается результат, сценарий продолжается. `INVALID`: дата не передаётся дальше, состояние остаётся `WAITING_DATETIME`, бот сообщает об ошибке.

# 19. Бизнес-правила

- BR-005-01: только `ДД.ММ.ГГГГ ЧЧ:ММ`.
- BR-005-02: свободный текст не распознаётся.
- BR-005-03: дата существует.
- BR-005-04: 24-часовой формат.
- BR-005-05/06: `scheduled_datetime > current_datetime`, равный и прошедший момент отклоняются.
- BR-005-07: проверка в timezone пользователя.
- BR-005-08/09: при ошибке состояние и фотография сохраняются.
- BR-005-10: ошибка не создаёт запись `posts`.
- BR-005-11: успешная дата передаётся следующему этапу.

# 20. Проверка будущего времени

При локальном `07.10.2026 14:30` ввод `07.10.2026 15:00` → `VALID`.

# 21. Проверка прошедшего времени

При локальном `07.10.2026 15:30` ввод `07.10.2026 15:00` → `PAST_DATETIME`.

# 22. Проверка равного текущего времени

При локальном `07.10.2026 15:00` ввод `07.10.2026 15:00` недопустим (`>` вместо `>=`).

# 23. FSM

Вход `WAITING_DATETIME`, при ошибке то же состояние. При успехе данные передаются в SPEC-009; после успешного завершения SPEC-009 — `IDLE`.

# 24. Sequence Flow — успешный сценарий

User → Telegram → DateTime Handler → Date Parser → Timezone conversion → Validation → Application Service → SPEC-009.

# 25. Sequence Flow — ошибка формата

User → Handler → Parser → Validation Error → Telegram Bot (пример формата) → `WAITING_DATETIME`.

# 26. Обработка неправильного формата

При вводе «завтра в пять» бот отвечает:

```text
⚠️ Я пока не понимаю такой формат.

Напиши дату и время так:

07.10.2026 17:00
```

FSM остаётся `WAITING_DATETIME`.

# 27. Обработка прошедшей даты

```text
⚠️ Это время уже прошло.

Укажи дату и время в будущем.

Например:
08.10.2026 15:00
```

# 28. Ошибки

- ERR-005-01 `INVALID_FORMAT`: строка не соответствует формату; подсказка, состояние не меняется.
- ERR-005-02 `INVALID_DATE`: календарная дата не существует; состояние не меняется.
- ERR-005-03 `INVALID_TIME`: время невозможно.
- ERR-005-04 `PAST_DATETIME`: момент уже наступил или прошёл.

# 29. Работа с timezone

Локальное время вводится без timezone. Пояс берётся из профиля, иначе из `DEFAULT_TIMEZONE`; для MVP значение по умолчанию — `Europe/Moscow`. Детальные правила — SPEC-006.

# 30. Пример преобразования

`07.10.2026 15:00` в `Europe/Moscow` → `2026-10-07 15:00:00+03:00` → `2026-10-07 12:00:00+00:00`. Передаётся UTC.

# 31. Данные БД

SPEC-005 не создаёт `posts`; подготавливает `scheduled_at_utc` и `timezone`. Запись выполняется в SPEC-009.

# 32. Handler contract

В `WAITING_DATETIME` обрабатывается текст: `handle_datetime_message(telegram_user_id: int, text: str) -> DateTimeHandlingResult` (логическая сигнатура).

# 33. DateTimeHandlingResult

Допустима модель с `success`, `utc_datetime`, `local_datetime`, `timezone`, `error_code`; эквивалентные внутренние исходы разрешены.

# 34. Application flow

Handler → Parser → Validation Service → Timezone Conversion → Post Service → Repository. Прямой SQL из handler запрещён.

# 35. Логирование

При успехе `INFO Publication datetime accepted user_id=123456789`; при ошибке формата `INFO Invalid publication datetime format user_id=123456789`; при прошедшем времени `INFO Past publication datetime rejected user_id=123456789`. Без лишних персональных данных.

# 36. Acceptance Criteria

- AC-005-01: после фото, при будущем моменте `07.10.2026 15:00` успешно распознан.
- AC-005-02: «завтра в пять» отклонено с подсказкой; FSM и фото сохраняются.
- AC-005-03/04: `07/10/2026 15:00` и `2026-10-07 15:00` отклоняются.
- AC-005-05: `31.02.2026 15:00` не принимается.
- AC-005-06/07: `07.10.2026 24:30` и `07.10.2026 15:60` отклоняются.
- AC-005-08/09: прошлое и равное текущему время отклоняются, поста нет, FSM сохранена.
- AC-005-10: будущее время в тот же день (14:59 → 15:00) принимается.
- AC-005-11: при ошибке фото повторно отправлять не нужно.
- AC-005-12: 15:00 в Москве преобразуется в 12:00 UTC.

# 37. Unit Tests

TC-005-01/02: `07.10.2026 15:00`, `01.12.2026 09:30` корректны в будущем. TC-005-03/04: «завтра», slash → `INVALID_FORMAT`. TC-005-05/06: `31.02`, месяц 13 → `INVALID_DATE`. TC-005-07/08: час 25, минуты 60 → `INVALID_TIME`. TC-005-09: прошлое → `PAST_DATETIME`. TC-005-10: будущее → `VALID`. TC-005-11: равное → `PAST_DATETIME`.

# 38. Integration Tests

IT-005-01: Telegram text → Handler → Parser → Timezone → Validation → UTC. IT-005-02/03: при ошибке `WAITING_DATETIME` и `telegram_file_id` сохраняются. IT-005-04: при успехе передача в SPEC-009.

# 39. E2E-сценарий — успешный ввод

`/start` → фото → запрос даты → `07.10.2026 15:00` → parse → timezone → проверка будущего → SPEC-009 → созданная публикация → подтверждение.

# 40. E2E-сценарий — ошибка и исправление

Фото → запрос даты → «завтра в пять» → подсказка → `WAITING_DATETIME` → `08.10.2026 17:00` → продолжение без нового фото.

# 41. Таблица тестовых значений

Будущие `07.10.2026 15:00`, `01.12.2026 09:30`, `31.12.2026 23:59` → `VALID`. Свободный текст, slash, ISO → `INVALID_FORMAT`. Несуществующие дни/месяцы → `INVALID_DATE`. Невозможное время → `INVALID_TIME`. Прошлый и текущий момент → `PAST_DATETIME`.

# 42. Definition of Done

Приём даты как текста; только строгий формат; календарь/час/минута; свободный текст; будущее строго `>`; timezone пользователя и UTC; ошибка сохраняет FSM/фото и не создаёт posts; успешная передача в SPEC-009; unit/integration/E2E тесты.

# 43. Результат SPEC-005

`local_datetime`, `timezone`, `scheduled_at_utc`; пример: `07.10.2026 15:00` в `Europe/Moscow` → `2026-10-07 15:00:00+03:00` и `2026-10-07 12:00:00+00:00`; вместе с фото передаётся SPEC-009.
