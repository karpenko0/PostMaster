# SPEC-006. Часовые зоны

**Проект:** Telegram-бот «PostMaster»
**Этап:** MVP
**Версия:** 1.0
**Статус:** к разработке

> Рабочая структурированная редакция переданного ТЗ: повторяющиеся примеры и последовательности сокращены, идентификаторы требований сохранены. Полный текст предоставлен пользователем в диалоге.

## 1–5. Назначение, цель, границы, зависимости

Дата пользователя интерпретируется в timezone пользователя (или `DEFAULT_TIMEZONE`), конвертируется в UTC для хранения, проверок и Scheduler; при отображении UTC переводится обратно. Timezone сервера не используется как пользовательская. В scope: хранение timezone пользователя и публикации, обе конвертации, дефолт `Europe/Moscow`, проверка будущего времени и локальное отображение. Вне scope: определение timezone по IP/геолокации/телефону, `/settings` (SPEC-041), выбор и смена timezone, пояс каналов и отдельный пояс публикации, отличный от пояса пользователя. Зависимости: SPEC-005, 007–010, 017, 018, 040, 041.

## 6–7. Принцип хранения

`07.10.2026 15:00` в `Europe/Moscow` → local `2026-10-07 15:00:00+03:00` → UTC `2026-10-07 12:00:00+00:00` → `posts.scheduled_at_utc`, `posts.timezone`. Нельзя хранить только naive локальное время.

## 8. User Stories

- US-006-01: ввод в локальном времени пользователя без ручного пересчёта UTC.
- US-006-02: хранение момента в UTC (15:00 Москва = 12:00 UTC).
- US-006-03: обратный показ 12:00 UTC как 15:00 Москва.
- US-006-04: пользователь с `timezone = null` работает с `Europe/Moscow`.

## 9–13. Источники и модели

Приоритет: `users.timezone`, затем конфигурационный `DEFAULT_TIMEZONE=Europe/Moscow`. Не прошивать дефолт строкой в handler/service. Timezone — IANA-строка, например `UTC`, `Europe/Berlin`, `America/New_York`. `users.timezone` — VARCHAR; публикация должна хранить `scheduled_at_utc` (DATETIME NOT NULL) и `timezone` (VARCHAR NOT NULL), использованную при создании.

## 14–17. Контракты

```python
convert_local_to_utc(local_datetime: datetime, timezone: str) -> datetime
convert_utc_to_local(utc_datetime: datetime, timezone: str) -> datetime
resolve_user_timezone(user_timezone: str | None, default_timezone: str) -> str
```

Допустимый интерфейс `TimezoneService.to_utc/to_local`; получение timezone профиля — через пользовательский сервис/репозиторий. Если пояс пользователя не задан или невалиден — используется дефолт.

## 18–24. Преобразование и сравнение

15:00 Москва → 12:00 UTC; 12:00 UTC → 15:00 Москва. Для будущего сравнивать aware UTC (`scheduled_at_utc > now_utc`), а не naive значение и не `datetime.now()` в локальном поясе ОС. При now=11:30 UTC значение 12:00 UTC принимается; при now=12:30 UTC — отклоняется.

## 25–26. Потоки

Создание: пользователь → Handler → User Service → timezone → local→UTC → Validation → Post Service → Database. Отображение: Database UTC → Post Service → timezone → UTC→local → Bot → пользователь.

## 27. Бизнес-правила

- BR-006-01…03: локальный ввод в пользовательском timezone; при отсутствии дефолт `Europe/Moscow` из конфигурации.
- BR-006-04…06: момент в БД — UTC; пояс пользователя отдельно; публикация сохраняет пояс, применённый при создании.
- BR-006-07: Scheduler получает UTC, не локальное время.
- BR-006-08: при показе UTC преобразуется в пояс пользователя/публикации.
- BR-006-09: timezone сервера не влияет на вычисления.
- BR-006-10: проверка будущего после нормализации.

## 28–30. Ошибки

ERR-006-01 `TIMEZONE_MISSING`: отсутствие пользовательского пояса не ошибка, применить `DEFAULT_TIMEZONE`. ERR-006-02 `TIMEZONE_INVALID`: неверное значение пользовательского пояса не использовать в расчёте, применить `DEFAULT_TIMEZONE`. Валидный пользовательский пояс имеет приоритет.

## 31–33. Контракты последующих этапов

UserRepository получает пользователя по Telegram ID. При создании поста передать `scheduled_at_utc` и `timezone` в Post Service. Scheduler работает с UTC и не вычисляет локальный пояс самостоятельно.

## 34–36. Отображение

`/my_posts` и `/cancel` отображают локальное время: для 12:00 UTC и Москвы — 15:00. Основной формат `DD.MM.YYYY HH:MM`, конвертация до форматирования; альтернативный формат (7 октября 2026 / 15:00) допустим.

## 37. Логирование

Допустимы `INFO User timezone resolved user_id=123456789 timezone=Europe/Moscow` и `INFO Publication datetime converted to UTC user_id=123456789`. Не писать на каждом техническом вызове без необходимости.

## 38. Acceptance Criteria

- AC-006-01/02: валидный пояс из профиля имеет приоритет, при NULL применяется `Europe/Moscow`.
- AC-006-03/04: 15:00 Москва ↔ 12:00 UTC; при показе строка `07.10.2026 15:00`.
- AC-006-05: сервер в UTC не меняет смысл пользовательского 15:00.
- AC-006-06/07: сравнение 12:00 UTC с 11:30/12:30 UTC принимает/отклоняет соответственно.
- AC-006-08/09: при создании поста поля `posts.timezone` и `posts.scheduled_at_utc` сохраняются.
- AC-006-10: `/my_posts` показывает 15:00 из сохранённого 12:00 UTC.

## 39. Unit Tests

TC-006-01/02: Москва 15:00 → 12:00 UTC и обратно. TC-006-03: NULL → дефолт. TC-006-04: независимость от timezone сервера. TC-006-05: будущее по `scheduled_at_utc > now_utc`.

## 40. Integration Tests

IT-006-01: User → SPEC-005 → timezone → UTC → SPEC-009. IT-006-02: сохранение 12:00 UTC и `Europe/Moscow` в БД. IT-006-03: чтение из БД и обратное преобразование в 15:00. IT-006-04: сценарий на сервере с timezone UTC.

## 41–43. E2E и таблица

E2E-006-01: фото → timezone пользователя → 15:00 Москва → 12:00 UTC → создание публикации и Scheduler → `/my_posts` показывает 15:00. E2E с дефолтом: `user.timezone = null`, `DEFAULT_TIMEZONE=Europe/Moscow`; те же UTC и пояс сохраняются. `07.10.2026 12:00 UTC` → `07.10.2026 12:00 UTC`.

## 44. Инварианты

INV-006-01: `scheduled_at_utc` всегда UTC. INV-006-02: Scheduler не использует локальное время напрямую. INV-006-03: timezone сервера не задаёт пользовательский пояс. INV-006-04: публикация содержит пояс создания. INV-006-05: при показе UTC преобразуется в local.

## 45. Definition of Done

Timezone пользователя и дефолт поддерживаются; local↔UTC работает; пояс пользователя и публикации сохранён; UTC хранится в БД; проверка времени aware и независима от сервера; Scheduler получает UTC; `/my_posts` и `/cancel` показывают local; unit, integration, E2E проходят.

## 46. Результат

Ввод → пояс пользователя → aware local → UTC → Database/Scheduler; отображение: Database UTC → пояс публикации → local → Telegram UI. Для MVP 15:00 Москва = 12:00 UTC, данные передаются SPEC-009.
