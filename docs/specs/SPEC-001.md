# SPEC-001. Foundation и базовая архитектура

Проект: Telegram-бот «PostMaster»
Этап: MVP
Статус: проектная спецификация

## 1. Цель

Задать технический фундамент PostMaster и единые границы слоёв приложения для реализации остальных спецификаций.

## 2. Scope

- Python 3.12+
- pyTelegramBotAPI
- SQLAlchemy
- APScheduler
- python-dotenv
- Pydantic
- структура bot/domain/services/publishers/repositories/database/utils
- Long Polling для MVP
- Dockerfile и docker-compose.yml
- базовое логирование
- подготовка к переходу на Webhook без изменения бизнес-логики

## 3. User Stories

- US-01. Как разработчик, я хочу иметь единый каркас проекта, чтобы новые функции добавлялись в определённые слои.
- US-02. Как оператор, я хочу запускать приложение из одной точки входа, чтобы бот и Scheduler стартовали согласованно.

## 4. Бизнес-правила

- BR-01. Бизнес-логика не должна находиться в Telegram handlers.
- BR-02. Доступ к данным выполняется через Repository.
- BR-03. Публикация выполняется через Publisher.
- BR-04. Scheduler использует Application Service, а не обращается напрямую к Telegram API.
- BR-05. MVP работает через Long Polling.

## 5. API / интерфейсные контракты

Внешний Telegram-контракт

На уровне Foundation фиксируется использование Telegram Bot API через pyTelegramBotAPI. Конкретные команды описаны в функциональных SPEC.

Внутренние интерфейсы

```python
class PostService: ...
class SchedulerService: ...
class PublicationService: ...
class UserService: ...
class Publisher:
    async def publish(self, post): ...
```

## 6. Данные и таблицы БД

На этом уровне отдельная таблица не создаётся. Используются таблицы users и posts, определённые в SPEC-007 и SPEC-008.

## 7. Основной сценарий

1. Система получает входные данные, относящиеся к данной спецификации.
2. Выполняются бизнес-правила и проверки этой SPEC.
3. При успешном результате состояние/данные изменяются согласно указанным контрактам.
4. При ошибке операция не должна нарушать ранее сохранённые данные; применяется предусмотренная этой SPEC обработка.

## 8. Критерии приёмки

- AC-01. Проект запускается на Python 3.12+.
- AC-02. Все обязательные зависимости подключены.
- AC-03. Присутствует единая точка входа.
- AC-04. Слои проекта физически разделены по утверждённой структуре.
- AC-05. Приложение может работать через Long Polling.
- AC-06. Dockerfile и docker-compose.yml присутствуют.

## 9. Тестирование

- TC-01. Smoke test импорта пакетов.
- TC-02. Smoke test запуска приложения с тестовой конфигурацией.
- TC-03. Проверка отсутствия циклической зависимости между слоями.

## 10. Ограничения

- Реализуются только требования, перечисленные в этой спецификации и исходном техническом задании PostMaster.
- Неописанные функции, поля, роли, интеграции и пользовательские сценарии не входят в scope данной SPEC.
