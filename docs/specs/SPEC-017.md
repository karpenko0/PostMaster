# SPEC-017. Команда `/my_posts`

**Проект:** Telegram-бот «PostMaster»
**Этап:** MVP
**Версия:** 1.0
**Статус:** реализовано

## 1. Назначение и цель

Команда `/my_posts` показывает пользователю его запланированные публикации, ожидающие выполнения. В ответе должны быть только записи текущего пользователя со статусом `PENDING`, отсортированные по `scheduled_at_utc` по возрастанию. Для каждой записи отображаются ID, локальные дата и время, а также читаемое название типа публикации.

## 2. Scope

- обработчик `/my_posts` в личном чате;
- поиск пользователя по `message.from_user.id`;
- запрос списка через `PostRepository.list_pending_by_user(user_id)`;
- фильтрация пользователя и статуса в SQL;
- сортировка ближайшей публикации первой;
- отображение времени в timezone, сохранённой для публикации;
- отображение Post ID и типа публикации;
- обработка неизвестного пользователя, пустого списка и ошибки чтения;
- разбиение длинного списка на несколько сообщений.

**Out of scope:** отмена (`SPEC-018`), изменение времени и содержания, история завершённых, `PROCESSING`, `FAILED`, `PUBLISHED`, `CANCELLED`, календарь и inline-редактирование.

## 3. Основной сценарий

```text
/my_posts → PostQueryService → UserService → User
                              → PostRepository.list_pending_by_user(user.id)
                              → сортировка → UTC в timezone публикации
                              → Telegram response
```

Пользователь ищется через `get_by_telegram_id(telegram_user_id)`. Если он не найден, репозиторий публикаций не вызывается и отправляется:

```text
Не удалось найти данные пользователя. Используйте /start.
```

## 4. Правила выборки и отображения

Контракт репозитория:

```python
list_pending_by_user(user_id: int) -> list[Post]
```

Запрос обязан фильтровать в БД одновременно по `posts.user_id = :user_id` и `posts.status = 'PENDING'`, сортировать по `scheduled_at_utc ASC` (при равном времени — по ID для устойчивого порядка). Нельзя получать все публикации или все `PENDING` с последующей фильтрацией в handler.

Время из `scheduled_at_utc` переводится через `convert_utc_to_local` в `Post.timezone`, зафиксированную при создании публикации. Для пользовательского текста используются подписи:

- `REMINDER` → `Напоминание`;
- `TELEGRAM` → `Telegram`.

Каждый элемент содержит, как минимум:

```text
#42
📅 20.10.2026 15:00
📌 Тип: Напоминание
```

Caption необязателен и в MVP может не показываться. При пустом списке отправляется `У вас нет запланированных публикаций.` Длинный ответ может состоять из нескольких Telegram-сообщений, сохраняя общий порядок.

## 5. Ошибки и логирование

Если загрузка пользователя/списка завершилась ошибкой, пользователю отправляется:

```text
Не удалось загрузить запланированные публикации.
Попробуйте позже.
```

Технические детали исключений и данные других пользователей в ответ не включаются. Логируются запрос и число результатов; сбой логируется без текста потенциально чувствительного исключения.

## 6. Acceptance Criteria

- **AC-017-01:** `/my_posts` работает для существующего пользователя.
- **AC-017-02:** показаны только `PENDING`.
- **AC-017-03:** показаны только записи текущего владельца; фильтрация выполняется в repository query.
- **AC-017-04:** порядок — `scheduled_at_utc ASC`.
- **AC-017-05:** дата и время отображены в timezone публикации, а не в UTC.
- **AC-017-06:** каждый элемент содержит `post.id`.
- **AC-017-07:** каждый элемент содержит локализованный тип.
- **AC-017-08:** пустой список обрабатывается понятным сообщением.
- **AC-017-09…11:** `PUBLISHED`, `CANCELLED`, `FAILED` не отображаются.
- **AC-017-12:** чужие публикации не доступны пользователю.

## 7. Проверки

Unit-тесты проверяют пустой список, формат записи, сортировку, преобразование timezone, подписи типов, разбиение длинного списка, неизвестного пользователя и обработку исключения. Repository/integration-тесты создают несколько пользователей и статусов, проверяют фильтр по владельцу и `PENDING`, порядок, локальное время и ответ handler через Telegram transport. E2E-сценарий: создать записи двум пользователям, запросить `/my_posts` от первого и убедиться, что в ответе только его `PENDING` записи в правильном порядке.

## 8. Инварианты

- Пользователь видит только собственные записи.
- `/my_posts` в MVP показывает только `PENDING`.
- UTC не отображается как пользовательское время без конвертации.
- Список всегда упорядочен ближайшей публикацией первой.
- Ошибка хранилища не раскрывает детали пользователю.
