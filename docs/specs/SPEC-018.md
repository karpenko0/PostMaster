# SPEC-018. Команда `/cancel`

**Проект:** Telegram-бот «PostMaster»
**Этап:** MVP
**Версия:** 1.0
**Статус:** реализовано

## 1. Назначение

Команда `/cancel <post_id>` отменяет только собственную ожидающую публикацию. Запись не удаляется: атомарный переход `PENDING → CANCELLED` в БД является источником истины. После успеха Scheduler job снимается best-effort.

## 2. Scope и зависимости

В scope входят handler, разбор положительного целого `post_id`, разрешение пользователя по Telegram ID, атомарная owner-scoped отмена, удаление задания Scheduler, понятные ответы и обработка ошибок.

Зависит от SPEC-007, SPEC-008, SPEC-010, SPEC-013 и SPEC-017. Не входят удаление записи, изменение расписания, отмена `PROCESSING`, `PUBLISHED`, `FAILED`, `CANCELLED`, массовая отмена и inline-кнопки.

## 3. Формат и пользовательские ответы

- `/cancel 42` — запросить отмену публикации 42.
- `/cancel` — `Укажите ID публикации.\n\nПример:\n/cancel 42`
- `/cancel abc` — `Некорректный ID публикации.\nПример: /cancel 42`
- Успех — `✅ Публикация #42 отменена.`
- Неизвестный пользователь — попросить начать с `/start`.
- Нет записи, чужая запись или иное неотменяемое состояние — безопасное общее сообщение без раскрытия существования чужого Post.
- `PROCESSING` — `Эта публикация уже выполняется и не может быть отменена.`
- `PUBLISHED` — `Эта публикация уже выполнена.`
- `FAILED` — информировать, что публикация завершилась с ошибкой и не может быть отменена.
- `CANCELLED` — `Эта публикация уже отменена.`

ID должен состоять только из ASCII-цифр и быть больше нуля. Ошибка валидации не вызывает запись в Repository.

## 4. Атомарная отмена и изоляция владельца

Repository contract:

```python
cancel_pending_post(post_id: int, user_id: int) -> bool
```

Операция выполняется одним условным `UPDATE`, содержащим одновременно `id = :post_id`, `user_id = :user_id`, `status = 'PENDING'`. `rowcount=1` означает успех; `rowcount=0` — отмена не произведена. Ни чтение статуса, ни удаление Scheduler job не заменяют эту атомарную проверку.

Только `PENDING → CANCELLED` разрешён обычной отменой. Если Scheduler уже выиграл гонку и перевёл запись в `PROCESSING`, отмена не может изменить её. Если отмена выиграла, последующий atomic claim не захватит `CANCELLED`.

## 5. Scheduler cleanup

После успешного коммита отмены вызывается `SchedulerService.remove_post(post_id)`. Возвращаемое значение «job отсутствует» не отменяет бизнес-успех. Исключение удаления логируется как warning; Post остаётся `CANCELLED`. Если остаточный callback всё же запустится, `PublicationService` не пройдёт `claim_post_for_processing`, поэтому Publisher не вызывается.

## 6. Логирование

Логируются запрос и исход по внутреннему `user_id`/`post_id`; при ошибке Scheduler — `WARNING Scheduler job removal failed post_id=...`. Текст исключения не пересылается пользователю и не включается в лог отмены.

## 7. Acceptance Criteria

- **AC-018-01:** `/cancel 42` извлекает `post_id=42`.
- **AC-018-02:** собственный `PENDING` становится `CANCELLED`.
- **AC-018-03:** чужой Post не меняется и не раскрывается.
- **AC-018-04…07:** `PROCESSING`, `PUBLISHED`, `FAILED`, `CANCELLED` не переходят повторно в `CANCELLED`.
- **AC-018-08:** после успеха вызван `remove_post(post_id)`.
- **AC-018-09:** отсутствие job не откатывает отмену.
- **AC-018-10:** оставшийся callback не вызывает Publisher.
- **AC-018-11…12:** отсутствие/некорректность ID дают инструкцию/ошибку до Repository update.

## 8. Тесты и инварианты

Тестируются parser и handler; owner-scoped conditional update; отмена допустимых и недопустимых статусов; повторная отмена; гонка `cancel`/`claim`; Scheduler job removal, отсутствие job и ошибка удаления; вызов оставшегося callback; сквозная цепочка `/my_posts → /cancel → CANCELLED → /my_posts`.

Инварианты: пользователь отменяет только собственные Post; физическое удаление запрещено; только `PENDING` может быть отменён; `CANCELLED` не публикуется; ошибка cleanup не меняет бизнес-результат.
