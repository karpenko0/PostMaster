# SPEC-004. Приём и обработка фотографии

**Проект:** Telegram-бот «PostMaster»  
**Этап:** MVP  
**Версия:** 1.0  
**Статус:** к разработке

---

# 1. Назначение

Данная спецификация описывает функциональность приёма фотографии от пользователя в Telegram, извлечение Telegram-идентификаторов изображения и передачу данных фотографии в дальнейший сценарий создания отложенной публикации.

Основная задача модуля — принять фотографию и сохранить достаточно данных для того, чтобы в момент публикации не скачивать и не хранить изображение на сервере, а повторно использовать Telegram `file_id`.

---

# 2. Цель

После отправки фотографии пользователем система должна:

1. определить, что входящее сообщение содержит фотографию;
2. получить данные фотографии из Telegram Update;
3. выбрать фотографию максимального доступного размера;
4. получить `file_id`;
5. получить `file_unique_id`;
6. получить технические метаданные изображения;
7. сохранить данные фотографии в текущем пользовательском сценарии;
8. перевести пользователя в состояние ожидания даты и времени;
9. запросить дату и время публикации.

---

# 3. Scope

В рамках SPEC-004 реализуются:

- приём сообщения Telegram типа `photo`;
- обработка массива `photo[]`;
- выбор максимального доступного изображения;
- получение `file_id`;
- получение `file_unique_id`;
- получение `file_size`;
- получение `width`;
- получение `height`;
- сохранение данных фотографии для дальнейшего создания публикации;
- изменение состояния пользователя;
- запрос даты и времени;
- обработка повторной фотографии в состоянии ожидания даты;
- обработка сообщения, не содержащего фотографию, если система ожидает фото.

---

# 4. Out of Scope

В данной спецификации не реализуются:

- скачивание изображения на сервер;
- изменение изображения;
- сжатие изображения;
- генерация превью;
- хранение бинарных файлов;
- OCR;
- AI Vision;
- публикация изображения;
- планирование публикации;
- VK API;
- видео;
- документы;
- альбомы;
- несколько изображений в одном посте;
- редактирование фотографии.

Эти функции либо относятся к другим спецификациям, либо предусмотрены на следующих этапах проекта.

---

# 5. Зависимости

SPEC-004 зависит от:

- **SPEC-002** — пользователь и `/start`;
- **SPEC-003** — FSM и управление состоянием диалога.

После успешного выполнения SPEC-004 сценарий переходит к:

- **SPEC-005** — ввод и валидация даты и времени.

# 6. Пользовательский сценарий

## 6.1. Основной сценарий

Пользователь выполняет:

```text
/start
```

Система переводит его в:

```text
WAITING_PHOTO
```

Пользователь отправляет фотографию.

Telegram передаёт сообщение боту.

Система:

1. определяет наличие `message.photo`;
2. получает массив `PhotoSize`;
3. выбирает изображение максимального доступного размера;
4. извлекает `file_id`;
5. извлекает `file_unique_id`;
6. извлекает `file_size`;
7. извлекает `width`;
8. извлекает `height`;
9. сохраняет данные фотографии в состоянии пользователя;
10. переводит пользователя в:

```text
WAITING_DATETIME
```

11. отправляет сообщение:

```text
📸 Фото получил!

Теперь укажи дату и время публикации.

Формат:

ДД.ММ.ГГГГ ЧЧ:ММ

Например:
07.10.2026 15:00
```

# 7. User Stories

## US-004-01. Отправка фотографии

**Как** SMM-менеджер  
**Я хочу** отправить фотографию PostMaster  
**Чтобы** запланировать её дальнейшую публикацию.

### Acceptance

После отправки фотографии бот должен принять её и запросить дату публикации.

---

## US-004-02. Использование Telegram file_id

**Как** пользователь  
**Я хочу**, чтобы бот сохранял мою фотографию без лишней загрузки файла на сервер  
**Чтобы** публикация не зависела от локального хранения изображения.

### Acceptance

Система сохраняет Telegram `file_id` и использует его в дальнейшем.

---

## US-004-03. Получение фотографии максимального размера

**Как** пользователь  
**Я хочу**, чтобы при публикации использовалась качественная версия отправленной фотографии  
**Чтобы** публикация не использовала уменьшенное Telegram-превью.

### Acceptance

Если Telegram предоставляет несколько `PhotoSize`, выбирается максимальный доступный вариант.

---

## US-004-04. Переход к выбору времени

**Как** пользователь  
**Я хочу** после отправки изображения сразу получить инструкцию по вводу даты  
**Чтобы** продолжить создание публикации без дополнительных действий.

### Acceptance

После успешной обработки фотографии пользователь переводится в `WAITING_DATETIME`.

# 8. Telegram API

## 8.1. Тип входящего сообщения

Используется Telegram Bot API объект:

```text
Message
```

Поле:

```text
photo
```

содержит массив:

```text
PhotoSize[]
```

---

# 9. Telegram PhotoSize

Telegram может передавать несколько размеров одного изображения.

Пример логической структуры:

```json
{
  "message_id": 101,
  "from": {
    "id": 123456789
  },
  "photo": [
    {
      "file_id": "AgAC_small",
      "file_unique_id": "AQAD123",
      "width": 90,
      "height": 90,
      "file_size": 2500
    },
    {
      "file_id": "AgAC_medium",
      "file_unique_id": "AQAD123",
      "width": 320,
      "height": 320,
      "file_size": 25000
    },
    {
      "file_id": "AgAC_large",
      "file_unique_id": "AQAD123",
      "width": 1280,
      "height": 1280,
      "file_size": 150000
    }
  ]
}
```

---

# 10. Алгоритм выбора фотографии

Система должна выбрать максимальный доступный `PhotoSize`.

При стандартном Telegram Update допустимо использовать последний элемент массива:

```python
photo = message.photo[-1]
```

Выбранный объект используется как основной источник данных изображения.

---

# 11. Получаемые данные

Из выбранного `PhotoSize` извлекаются:

| Поле | Обязательность | Назначение |
|---|---:|---|
| `file_id` | Да | повторная отправка изображения |
| `file_unique_id` | Да | стабильный идентификатор Telegram-файла |
| `file_size` | Нет | технические метаданные |
| `width` | Да | ширина изображения |
| `height` | Да | высота изображения |

---

# 12. file_id

## 12.1. Назначение

`file_id` используется Telegram для повторной отправки уже загруженного файла.

Пример:

```text
AgACAgIAAxkBAAIBFW...
```

Именно это значение должно использоваться при последующей отправке изображения.

---

# 13. file_unique_id

`file_unique_id` используется как постоянный Telegram-идентификатор файла.

В отличие от `file_id`, он не используется непосредственно для отправки изображения.

Сохраняется для идентификации файла.

---

# 14. Хранение изображения

В MVP изображение не должно обязательно загружаться на файловую систему сервера.

Запрещено строить основной сценарий вокруг:

```text
/downloads/photo1.jpg
```

или:

```text
/uploads/123.jpg
```

Основной механизм:

```text
Telegram file_id
```

---

# 15. FSM

До отправки фотографии пользователь должен находиться в состоянии:

```text
WAITING_PHOTO
```

После успешной обработки фотографии:

```text
WAITING_DATETIME
```

Схема:

```text
WAITING_PHOTO
    │
    │ PHOTO
    ▼
photo accepted
    │
    ▼
WAITING_DATETIME
```

---

# 16. Данные FSM

В состоянии пользователя должны быть доступны данные фотографии:

```text
telegram_file_id
telegram_file_unique_id
file_size
width
height
```

Минимально обязательное значение:

```text
telegram_file_id
```

# 18. Бизнес-правила

## BR-004-01

Система принимает фотографию только из Telegram-сообщения, содержащего `photo`.

---

## BR-004-02

Основным идентификатором изображения для дальнейшей публикации является:

```text
file_id
```

---

## BR-004-03

Физическое скачивание изображения не требуется.

---

## BR-004-04

Если Telegram передал несколько размеров изображения, выбирается максимальный доступный размер.

---

## BR-004-05

После успешной обработки фотография должна быть доступна для следующего шага сценария.

---

## BR-004-06

После успешного приёма пользователь переводится в:

```text
WAITING_DATETIME
```

---

## BR-004-07

После обработки бот обязан запросить дату и время.

---

## BR-004-08

Фотография сама по себе не создаёт отложенную публикацию в БД.

Публикация создаётся только после получения и успешной проверки даты и времени.

---

## BR-004-09

Если пользователь отправляет новую фотографию до ввода даты, новая фотография заменяет ранее выбранную фотографию для текущего сценария.

После этого бот снова запрашивает дату и время.

# 21. Repository API

Создание записи в `posts` непосредственно из photo handler не требуется.

Handler должен передать данные дальше через application layer.

Недопустимая архитектура:

```text
Telegram Handler
      ↓
raw SQL
```

Предпочтительная цепочка:

```text
Telegram Handler
      ↓
Application Service
      ↓
Repository
```

Фактическая запись создаётся после получения даты.

      ↓

      ↓

# 26. Неверный тип сообщения

Если пользователь находится в:

```text
WAITING_PHOTO
```

и вместо фотографии отправляет текст, система не должна переходить к следующему состоянию.

Ответ:

```text
Отправь фотографию, которую нужно опубликовать.
```

Состояние остаётся:

```text
WAITING_PHOTO
```

---

# 27. Повторная фотография

Сценарий:

```text
PHOTO A
↓
WAITING_DATETIME
↓
PHOTO B
```

В MVP новая фотография заменяет предыдущую.

FSM данные должны быть обновлены:

```text
PHOTO A → removed from current state
PHOTO B → current photo
```

Состояние остаётся:

```text
WAITING_DATETIME
```

После этого бот снова запрашивает дату.

---

# 28. Ошибки обработки

## ERR-004-01

Telegram Update не содержит `photo`.

Действие:

- не менять FSM;
- запросить фотографию.

---

## ERR-004-02

Массив `photo` пуст.

Действие:

- не сохранять данные;
- не переходить в `WAITING_DATETIME`;
- зарегистрировать ошибку в логах.

---

## ERR-004-03

У выбранного объекта отсутствует `file_id`.

Действие:

- обработку считать неуспешной;
- не создавать публикацию;
- не переходить к следующему этапу.

---

# 29. Логирование

При успешной обработке допускается лог:

```text
INFO Photo received user_id=123456789
```

Допускается:

```text
INFO Photo selected width=1280 height=1280
```

Не следует логировать бинарное содержимое изображения.

---

# 30. Безопасность

`file_id` не является Bot Token, но его не следует без необходимости показывать пользователю.

Пользовательскому интерфейсу не требуется выводить:

```text
file_id
file_unique_id
```

Они используются только внутри системы.

---

# 31. Производительность

Обработка фотографии не должна зависеть от физического размера файла на сервере, поскольку файл не скачивается.

Основные операции:

```text
Telegram Update
→ metadata extraction
→ FSM update
```

Это позволяет уменьшить:

- использование дискового пространства;
- сетевой трафик сервера;
- время обработки;
- требования к хранилищу.

---

# 33. Acceptance Criteria

## AC-004-01 — Приём фотографии

**Given** пользователь находится в `WAITING_PHOTO`  
**When** пользователь отправляет фотографию  
**Then** бот принимает сообщение.

---

## AC-004-02 — Получение file_id

**Given** Telegram передал массив `PhotoSize`  
**When** система обрабатывает сообщение  
**Then** извлекается `file_id`.

---

## AC-004-03 — Выбор максимального размера

**Given** Telegram передал несколько размеров:

```text
90x90
320x320
1280x1280
```

**When** система выбирает изображение  
**Then** используется объект `1280x1280`.

---

## AC-004-04 — Получение file_unique_id

**Given** фотография успешно принята  
**When** система извлекает метаданные  
**Then** сохраняется `file_unique_id`.

---

## AC-004-05 — Без локального файла

**Given** пользователь отправляет фотографию  
**When** система обрабатывает её  
**Then** успешная обработка не требует создания файла изображения на диске.

---

## AC-004-06 — Переход состояния

**Given** фотография успешно обработана  
**When** данные сохранены в текущем сценарии  
**Then** состояние пользователя становится:

```text
WAITING_DATETIME
```

---

## AC-004-07 — Запрос даты

**Given** фотография успешно принята  
**Then** пользователь получает подсказку:

```text
ДД.ММ.ГГГГ ЧЧ:ММ
```

---

## AC-004-08 — Текст вместо фотографии

**Given** пользователь находится в `WAITING_PHOTO`  
**When** он отправляет текст  
**Then**:

- состояние не меняется;
- публикация не создаётся;
- бот повторно просит отправить фотографию.

---

## AC-004-09 — Повторная фотография

**Given** пользователь уже отправил фотографию и находится в `WAITING_DATETIME`  
**When** пользователь отправляет другую фотографию  
**Then** новая фотография становится текущей для создаваемой публикации.

---
