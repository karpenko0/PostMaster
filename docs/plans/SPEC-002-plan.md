# План разработки SPEC-002 «Пользователь и команда /start»

Статус плана: выполнен. Все задачи проверены тестами, см. раздел 4.

## 1. Цель

Регистрировать пользователя по `/start` без дубликатов и переводить его в состояние `WAITING_PHOTO`.
Требования: US-01, US-02, AC-01…AC-04, TC-01…TC-04, BR-01…BR-04 из `docs/specs/SPEC-002.md`.

## 2. Решения, принятые при планировании

Спецификация не отвечает на часть вопросов. Ниже выбран вариант и причина. Все решения можно изменить.

| № | Решение | Обоснование |
|---|---|---|
| D1 | Состояние `WAITING_PHOTO` хранится в памяти через `StateMemoryStorage` pyTelegramBotAPI, поле в `users` не добавляется | Таблица в §6 SPEC-002 не содержит поля состояния, а §10 запрещает неописанные поля. Следствие: после перезапуска состояние сбрасывается |
| D2 | `DEFAULT_TIMEZONE` по умолчанию `UTC`. В `users.timezone` хранится NULL, эффективный пояс вычисляется при чтении (BR-04) | Спецификация не задаёт значение по умолчанию. NULL позволяет менять `DEFAULT_TIMEZONE` без правки данных |
| D3 | Повторный `/start` обновляет `username` и `first_name`, если они изменились. Пояс и `created_at` не меняются, запись не пишется, если данные совпали | Пересмотрено при закрытии вопросов. Контракт §5 (`get_or_create`) обновление не описывает, но в §6 есть `updated_at` («Дата изменения»). Без обновления `username` устаревал бы. Было: не обновлять |
| D4 | Таблицы создаются при старте через `Base.metadata.create_all` | Alembic запланирован вместе с SPEC-027 (решение D8 из SPEC-001) |
| D5 | Ошибка регистрации: исключение логируется, приветствие не отправляется, состояние и данные не меняются, пользователь получает короткий ответ «Не удалось обработать /start. Попробуйте ещё раз немного позже.» | Пересмотрено при закрытии вопросов. §7 п. 4 требует сохранности данных, текст ответа в SPEC-002 не описан. Молчание оставляло пользователя без ответа. Было: без ответа |
| D6 | Слои: модель в `database/models.py`; SQL и сессии в `repositories/user_repository.py`; правила в `services/user_service.py`; `handlers/start.py` разбирает сообщение и отвечает | TC-03 запрещает `services` импорт `database` и `sqlalchemy`, `handlers` — импорт `repositories` |
| D7 | Параллельный `/start` от одного пользователя: нарушение уникальности `telegram_user_id` перехватывается, и запись читается заново | BR-01 и AC-02 при параллельных обновлениях |
| D8 | Порядок в обработчике: запись в БД → приветствие → состояние | AC-03, затем AC-04: фото ожидается после ответа |
| D9 | `create_bot` создаёт собственное хранилище состояний | Хранилище по умолчанию общее на весь процесс, поэтому тесты влияли бы друг на друга |

## 5. Риски и ограничения

- Найдено при проверке: фейковый Telegram не читал `offset` в `getUpdates`. pyTelegramBotAPI шлёт этот метод как GET с телом формы, а `request.post()` в aiohttp для GET возвращает пустой словарь. Поэтому каждое обновление доставлялось повторно, и обработчик запускался несколько раз. В тестах SPEC-001 это не было видно, потому что бот останавливался после первого обновления. Исправлено в `tests/fake_telegram.py`. Ошибка была в тестовой инфраструктуре, а не в приложении.
- Часовые пояса проверяются через `zoneinfo`, то есть по системной базе IANA. Наличие этой базы в образе `python:3.12-slim` не проверено: Docker в этой среде недоступен. На Windows потребуется пакет `tzdata`, которого в зависимостях нет (AC-02 его не перечисляет).
- Состояние `WAITING_PHOTO` существует только в памяти процесса (D1). Перезапуск бота сбрасывает сценарий до повторного `/start`.
- Реальный Telegram из песочницы недоступен. Проверка выполнена на fake API, как и в SPEC-001.
- `create_all` не сопровождает изменения схемы. Alembic появится вместе с SPEC-027 (D4).
- Раньше `/start` в групповых чатах регистрировал пользователя. С D14 SPEC-003 в группах `/start` не обрабатывается (вопрос 5 закрыт).

## 6. Вопросы и их статус

1. Значение `DEFAULT_TIMEZONE` по умолчанию. **Закрыто:** `UTC` (D2). Пояс задаёт оператор
   в `.env`, пример в `.env.example`.
2. Сохранять `WAITING_PHOTO` между перезапусками? **Закрыто: нет.** Состояние остаётся в памяти
   (D1). Перезапуск сбрасывает сценарий, это написано в README.
3. Обновлять `username` и `first_name` при повторном `/start`? **Закрыто: да** (D3, пересмотрено).
   Обновляются при изменении вместе с `updated_at`. Тесты:
   `test_users::test_repeated_start_with_new_name_updates_profile_only`,
   `test_start_command::test_repeated_start_stores_changed_name`.
4. Ответ пользователю при ошибке регистрации? **Закрыто: да** (D5, пересмотрено). Короткий ответ,
   состояние не меняется. Тест: `test_start_command::test_failed_registration_keeps_data_and_state`.
5. Работа `/start` в групповых чатах? **Закрыто: только личные чаты** (D14 SPEC-003). В группе
   `/start` не регистрирует пользователя (`test_dialog_flow::test_group_chat_messages_are_ignored`).
   Причина: владелец публикации определяется `telegram_user_id`, а проверка прав доступа
   запланирована в SPEC-024 (см. `services/user_service.py`).
