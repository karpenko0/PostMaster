# План разработки SPEC-003 «FSM и управление состоянием диалога»

Статус плана: выполнен. Все задачи проверены тестами, см. раздел 4.

## 1. Цель

Реализовать конечный автомат сценария создания публикации: состояния `IDLE`, `WAITING_PHOTO`, `WAITING_DATETIME`, переходы по BR-01…BR-04 и обработку фотографии на шаге даты.
Требования: US-01, AC-01…AC-04, TC-01…TC-03, BR-01…BR-04 из `docs/specs/SPEC-003.md`.

## 2. Решения, принятые при планировании

Спецификация не отвечает на часть вопросов. Ниже выбран вариант и причина. Все решения можно изменить.

| № | Решение | Обоснование |
|---|---|---|
| D1 | Переходы заданы явной таблицей `TRANSITIONS` в `domain/dialog.py`. Недопустимое событие не меняет состояние | AC-02 требует только утверждённых переходов. Таблица проверяется тестом по всем парам «состояние — событие» |
| D2 | Хранилище: порт `DialogStore` в `services` (Protocol), реализация `TelebotDialogStore` в `bot` на состояниях pyTelegramBotAPI, в памяти процесса. Черновик (`file_id` фото) — данные состояния | Продолжение решения D1 SPEC-002. §6 SPEC-003 разрешает хранить данные публикации как состояние диалога. Слой `services` не импортирует telebot |
| D3 | Состояние записывается раньше данных | `StateMemoryStorage.set_data` выбрасывает `RuntimeError`, если записи состояния нет. Запись состояния создаёт её |
| D4 | `/start` переводит в `WAITING_PHOTO` из любого состояния и очищает черновик | BR-01 безусловен. «Новый сценарий» из US-02 SPEC-002 означает пустой черновик |
| D5 | Фото в `WAITING_DATETIME` заменяет предыдущее, состояние остаётся, бот снова просит дату | BR-04 и TC-03. В черновике хранится только фото, поэтому замена — это перезапись одного поля |
| D6 | Недопустимое сообщение (событие не разрешено в текущем состоянии, либо сообщение не текст и не фото): состояние не меняется, бот присылает подсказку для текущего шага | Спецификация не описывает ответ на недопустимое сообщение (TC-02 требует проверки). Подсказка нужна, чтобы пользователь понимал шаг (US-01). Текст подсказки — решение плана |
| D7 | Неверная дата (не по формату или в прошлом): состояние `WAITING_DATETIME` сохраняется, бот присылает подсказку с форматом | Продолжение D6 |
| D8 | Формат даты до отдельной спецификации: `ДД.ММ.ГГГГ ЧЧ:ММ` в поясе пользователя (`users.timezone` или `DEFAULT_TIMEZONE`, BR-04 SPEC-002). Только будущее время. Хранится в UTC | В SPEC-003 правила даты не описаны, но `VALID_DATETIME` требует проверки. Вариант временный, см. открытый вопрос 2 |
| D9 | «Создание поста» (BR-03, AC-03): `PostService.create_post` возвращает доменный `Post` и ничего не записывает. Черновик очищается только после успешного вызова | §6 запрещает новые постоянные таблицы. По SPEC-001 §6 таблица `posts` определена в SPEC-008, то есть позже. Открытый вопрос 1 |
| D10 | После создания поста явно сохраняется `IDLE`, черновик очищается | AC-03 и BR-03 |
| D11 | Операции над одним пользователем в одном чате выполняются по очереди (`asyncio.Lock` на пару `(user_id, chat_id)`). Блокировка не держится при отправке ответа | Telegram-обработчики идут параллельно. Без блокировки два фото могут перезаписать друг друга |
| D12 | Тексты ответов живут в `handlers/dialog.py`. Сервис возвращает исход (`DialogOutcomeKind`) и состояние | BR-01: логика не в обработчиках. Тексты относятся к представлению |
| D13 | `UserState` из SPEC-002 заменён на `DialogState` в `domain/dialog.py` | Одно место для состояний диалога |
| D14 | `/start` и обработчики шагов работают только в личных чатах (`chat_types=["private"]`) | В группе бот отвечал бы подсказкой на каждое сообщение. Закрывает открытый вопрос 5 SPEC-002. Меняет поведение `/start` в группах |

## 5. Риски и ограничения

- Состояние и черновик существуют только в памяти процесса (D2). Перезапуск сбрасывает сценарий.
- Пост не сохраняется в БД (D9). Сообщение «Публикация создана» подтверждает переход, но не запись. Запись появится вместе с таблицей `posts` (SPEC-008).
- Альбом из нескольких фото приходит отдельными сообщениями. Каждое фото заменяет предыдущее (открытый вопрос 5).
- Перевод времени (DST) не учитывается: `datetime.replace(tzinfo=...)` даёт неверное время внутри «дыры» перехода. Учёт DST относится к SPEC-006.
- Реальный Telegram из песочницы недоступен. Проверка выполнена на fake API.
- Хранилище pyTelegramBotAPI: `set_data` без записи состояния выбрасывает `RuntimeError`, а `get_data` отдаёт внутренний словарь. Учтено в адаптере (D3, копия данных). Эти детали нужно учитывать в любом новом использовании хранилища.
- Найдено при проверке группового чата: фото с `chat_type` по умолчанию «private» тоже попадало в обработчики. Ошибка была в тестовом фейке, не в приложении. Параметр `chat_type` добавлен во все методы фейка.

## 6. Вопросы и их статус

1. Запись поста. **Закрыто:** пост сохраняется в SPEC-008 вместе с таблицей `posts`
   (SPEC-001 §6). До этого «Публикация создана» — ответ бота без записи (D9). AC-03 и BR-03
   выполнены в объёме SPEC-003.
2. Формат и правила даты. **Открыто.** Формат `ДД.ММ.ГГГГ ЧЧ:ММ` в поясе пользователя оставлен
   временным (D8). В репозитории нет спецификации, которая описывает ввод даты и часовые пояса.
   Нужны её текст или решение владельца проекта.
3. Тексты ответов. **Закрыто:** оставлены текущие формулировки в `handlers/dialog.py` (D12).
   Их можно заменить одним изменением в этом файле.
4. Таблицы `users` и `posts` (SPEC-007). **Открыто.** Текста SPEC-007 в репозитории нет. Схема
   `users` соответствует SPEC-002 §6, это проверено запуском на временной БД. Если SPEC-007
   меняет `users`, понадобится миграция (SPEC-027).
5. Альбомы. **Закрыто:** в MVP каждое фото альбома приходит отдельным сообщением и заменяет
   предыдущее (BR-04). Пост создаётся из последней фотографии. Обработка альбома целиком —
   отдельная задача, если она понадобится.
6. Состояние диалога в памяти. **Закрыто:** хранится в памяти процесса (D2). Перезапуск сбрасывает
   сценарий, это указано в README.
7. Группы. **Закрыто:** только личные чаты (D14), см. вопрос 5 SPEC-002.
