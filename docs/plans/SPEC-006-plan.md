# План SPEC-006 — часовые зоны

Статус: преобразование/разрешение поясов реализовано, интеграция с хранилищем постов и UI последующих команд отложена до SPEC-008…010/017/018.

## Цель и границы

Приоритет timezone профиля над конфигурацией, fallback при отсутствии **или невалидности**, обе конвертации local↔UTC, независимость от TZ сервера, использование UTC для сравнения и передачи следующему сервису. Не реализовать настройки, выбор пояса, IP/геолокацию, записи публикаций, команды и Scheduler-job сверх предоставленных спецификаций.

## Решения

| № | Решение | Причина |
|---|---|---|
| D1 | `domain/timezone.py`: `resolve_user_timezone`, `convert_local_to_utc`, `convert_utc_to_local`; без зависимостей от Telegram/БД/системных часов | §14–17, матрица слоёв SPEC-001; единый источник правил |
| D2 | Проверить `default_timezone` через `ZoneInfo`, при пустом/неверном пользовательском значении вернуться к нему; неверный **дефолт** считать ошибкой конфигурации, не брать timezone ОС | ERR-006-01/02. Settings уже валидирует дефолт, функция защищает прямые вызовы |
| D3 | Для naive local attach `ZoneInfo(timezone)`, для aware local сохранить момент через `astimezone`; результат всегда aware UTC | Ввод из SPEC-005 naive, результат §14; aware-вход нельзя переписывать через `.replace(tzinfo=...)` с изменением момента |
| D4 | Обратный конвертер принимает только aware datetime с UTC-смещением 0; naive из SQLite должен восстановить UTC в репозитории | §15, INV-006-01/05; иначе результат мог бы зависеть от TZ сервера |
| D5 | SPEC-005 вызывает общий конвертер local→UTC; успешный handler форматирует результат после обратной конвертации из UTC | §20, §36, BR-006-08/10; сохранить текст ответа SPEC-003 без перестройки сценария |
| D6 | `User.effective_timezone` и `UserService.timezone_of` используют resolver, в том числе для пользователя без записи; значение users.timezone не переписывается при ошибке | §9, ERR-006-02; настройки изменения timezone вне scope (SPEC-041) |
| D7 | Временный DTO `Post` получает обязательный timezone, `PostService` отказывает при naive/non-UTC моменте и неверном поясе; `scheduled_at_utc` — явное alias к существующему `scheduled_at` | INV-006-01/04. Это **не** запись в таблицу posts из SPEC-008, контракты остаются совместимыми для читателей DTO |
| D8 | Scheduler уже настроен на UTC, но работающих заданий нет; не добавлять вызов Scheduler или persistence | SPEC-009/010; §33 требует будущий контракт, а не выдуманный сценарий публикации |
| D9 | Не добавлять специальные правила для DST gap/fold; `zoneinfo` использует стандартное `fold=0` при naive local | ТЗ SPEC-006 не определяет политику для двусмысленного/пропущенного часа; не изобретать её |
| D10 | Для проверки примеров 07.10.2026 замораживать `now`; менять TZ через `tzset` в тестах с обязательным восстановлением | Примеры устарели на текущую дату; §23, TC-006-04 требует независимости от времени сервера |

## Этапы проверки

1. Добавить спецификацию, план и конвертеры (TC-006-01…05).
2. Подключить UserService/SPEC-005/handler, проверить fallback на реальном профиле users и fake Telegram (IT-006-01/04).
3. Защитить контракт временной модели публикации: UTC и IANA-пояс; проверить передачу в PostService. Убедиться, что Scheduler конфигурирован в UTC.
4. Запустить полный `pytest` на Python 3.12, `ruff check`, `ruff format --check`, `git diff --check`; зафиксировать блокировки критериев по SPEC-008…010/017/018 в отчёте.

## Приёмка, которая требует последующих спецификаций

AC-006-08/09, IT-006-02/03, E2E §41–42 и DoD про БД требуют таблицу/репозиторий `posts` (SPEC-008) и реальное создание (SPEC-009). `/my_posts` (AC-006-10) — SPEC-017, `/cancel` — SPEC-018, фактические задания Scheduler — SPEC-010. Функция UTC→local проверяется отдельно, но сквозной UI этих команд пока отсутствует. Нельзя объявить эти критерии выполненными по тесту модели-заглушки.
