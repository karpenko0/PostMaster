# План SPEC-007 — модель данных пользователей

Статус: модель и сценарий регистрации реализованы; FK на `posts` и миграция уже существующих БД требуют следующих спецификаций.

## Цель

Уточнить `users` по §8: nullable `first_name`, сохранив PK/UNIQUE, UTC-даты, timezone и регистрацию через `/start`. Дать доступ к поиску User по Telegram ID, исключить дубли при конкурентных запросах и обновлять Telegram-поля без потери внутреннего ID и timezone.

## Решения

| № | Решение | Почему |
|---|---|---|
| D1 | `UserModel.first_name` становится nullable, доменная модель и сигнатуры UserRepository/UserService принимают `str | None` | §8/15, BR-007-05, AC-007-05; схема из SPEC-002 раньше требовала NOT NULL |
| D2 | Отсутствие имени в приветствии — отдельный текст без подстановки `None`, прежний текст с именем не меняется | BR-007-05: основная логика не должна блокироваться и выдавать техническое `None` пользователю |
| D3 | Существующие `add`, `find_by_telegram_id`, `update_profile` продолжают работать; репозиторий получает совместимый alias `get_by_telegram_id` (§31), сервис — одноимённый метод | Совместимость SPEC-002 и контракт SPEC-007 без переписывания старых клиентов; идентификатор всегда Telegram ID |
| D4 | Логировать создание, нахождение существующего пользователя и обновление только с ID, без имени/username. Ошибку регистрации handler логирует по ID и типу исключения, без SQL-параметров/traceback; фиктивный ID не выдаёт | §49/50; исключение SQLAlchemy может содержать персональные поля; сохранён ответ SPEC-002 при ошибке |
| D5 | Конкурентные вызовы используют уже имеющийся UNIQUE в БД + перехват DuplicateTelegramUserError и повторный поиск. Тест с несколькими реальными конкурентными транзакциями с nullable-полями | §38/54, AC-007-03, без новой ручной блокировки для одного процесса |
| D6 | `users.id` остаётся внутренним INTEGER PK, а `telegram_user_id` — BIGINT UNIQUE NOT NULL с индексом. Username не уникален; допускается его исчезновение | §6–14, AC-007-07/12; пользователи могут иметь одинаковый username в фейке |
| D7 | `timezone` при `/start` не задаётся/не перезаписывается; по умолчанию вычисляется в SPEC-006 при использовании, а не записывается в поле | §16, §28, AC-007-08/09, настройки вне scope (SPEC-041) |
| D8 | `posts` и FK `posts.user_id → users.id` не создаются до SPEC-008, а PostService пока возвращает лишь временный DTO с внешним `owner_telegram_id` | SPEC-007 §5, §21/22 и AC-007-10 зависят от модели SPEC-008/009; нельзя выдавать временную модель за запись публикации |
| D9 | Существующей SQLite-таблице с `first_name NOT NULL` нужна миграция: SQLAlchemy `create_all` её не изменяет. Не переписывать таблицу автоматически в startup: версионированные миграции — SPEC-027 | Предсказуемый запуск, сохранение существующих данных и ограничений. Старый DB не поддерживает nullable имя до миграции; явно отражено в README и приёмке |

## Этапы

2. Изменить тип/nullable в домене, ORM, репозитории, сервисе и обработчике; логирование по §50.
3. Проверить схему/UNIQUE/индекс, nullable-имена, смену и удаление username, неизменность id/created_at/timezone, поиск по Telegram ID, параллельную регистрацию.
4. Сквозной `/start` на fake Telegram и реальной SQLite; полная регрессия SPEC-001…006.
