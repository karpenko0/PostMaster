# План SPEC-005 — ввод и валидация даты и времени

Статус: выполнена часть, относящаяся к SPEC-005; сквозное сохранение поста отложено до SPEC-008/009.

## Цель и границы

Строгая дата `ДД.ММ.ГГГГ ЧЧ:ММ`, существующие календарная дата и время, строго будущий момент с учётом timezone пользователя, DTO с локальным и UTC временем, ошибки с точными подсказками и сохранением FSM-фото. Без естественного языка, создания строки `posts` и планировщика. Полный список требований: `docs/specs/SPEC-005.md`.

## Решения

| № | Решение | Обоснование |
|---|---|---|
| D1 | `parse_publication_datetime(value, timezone, now) -> ParsedPublicationDateTime` в domain/schedule.py; при ошибке `DateTimeValidationError(code)` | Контракт §15–18, различение ERR-005-01…04 без разбора текста исключения |
| D2 | Полное совпадение ASCII-цифр/разделителей/длины регулярным выражением до `strptime`; сначала отдельно проверка календаря, затем `strptime` для времени | `strptime` принимает однозначные цифры, а §9 требует ровно две. Сначала календарь, чтобы различать INVALID_DATE и INVALID_TIME |
| D3 | `now` — aware datetime, сравнение в UTC; naive now отвергается как ошибка вызывающего кода | Не зависит от timezone машины, тестируется при фиксированном now; §19 BR-005-05…07 |
| D4 | Пояс берётся через существующий `UserService.timezone_of`; дефолт `Europe/Moscow` в Config и .env.example, запись users.timezone не меняется | §29 SPEC-005 уточняет ранее не заданный в SPEC-002 дефолт; пользовательский пояс имеет приоритет |
| D5 | Для существующего `DialogService.receive_text` исход `DATETIME_INVALID` несёт код, `POST_CREATED` несёт DTO, timezone и локальное время; handler выбирает точные тексты §26/27 | Достаточно для интерфейса §32/33 без дополнительного Telegram-зависимого сервиса |
| D6 | Неверная дата и неверное время показывают подсказку формата §26, прошедшая — §27 | §28 задаёт код, но отдельного текста для INVALID_DATE/INVALID_TIME нет |
| D7 | Существующий `PostService.create_post` (пока in-memory DTO) получает photo_file_id, scheduled_at UTC, timezone и local_datetime; после его успешного возврата сохранён прежний переход в IDLE/ответ SPEC-003 | Передача данных SPEC-009 по §43, без новых SQL-операций. Это **не** реальная запись `posts`; создание в БД/подтверждение реального создания — SPEC-008/009. При сбое сервисного вызова FSM/фото не очищаются |
| D8 | Старый `parse_local_datetime` остаётся только как совместимость для тестов/внутреннего контракта SPEC-003; новый поток использует строгий API | Переход без регрессии для старого API; строгий ввод Telegram без `.strip()` |
| D9 | Нормализация IANA через ZoneInfo (существующий подход). Отдельное поведение для DST-gap/fold не добавляется | §17/29 делегирует такие правила SPEC-006, которая ещё не предоставлена |
| D10 | Фиксированные часы в тестах: 07.10.2026 11:59 UTC (Москва 14:59); реальные текущие даты из тестового helper не используются для примеров из ТЗ | Сегодня даты из примеров уже в прошлом; тесты не должны зависеть от дня запуска |

## Этапы

1. Сохранить требования и решения (этот план).
2. Реализовать доменный API и коды ошибок; изменить DEFAULT_TIMEZONE.
3. Встроить API в DialogService/Handler; передать UTC, timezone и local_datetime в PostService; сохранить фото и FSM при ошибке.
4. TC-005-01…11 + некорректная ширина/пробелы/високосный год; IT-005-01…04 через service spy и fake Telegram; E2E «ошибка → исправление» до существующего сервисного контракта.
5. Проверить полный pytest на Python 3.12, Ruff, регрессию SPEC-001…004; отразить ограничение SPEC-008/009 в отчёте.

## Риски и дальнейшие задачи

- SPEC-006 предоставлена: она не задаёт специальную политику DST для пропущенных/двойных часов; используется поведение стандартного `zoneinfo` (см. SPEC-006 D9).
- SPEC-008/009 не реализованы: тесты не могут подтвердить существование записи `posts` или настоящей отложенной публикации. Уже существующий ответ «Публикация создана» принадлежит заглушке SPEC-003, а не реальной записи; это должно быть исправлено в SPEC-009.
- Выбор `Europe/Moscow` вместо `UTC` влияет на приложения без явного `DEFAULT_TIMEZONE`; в развертываниях с переменной окружения значение остаётся операторским.
