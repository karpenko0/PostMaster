# План разработки SPEC-004 «Приём и обработка фотографии»

Статус плана: выполнен. Все задачи проверены тестами, см. раздел 4.

## 1. Цель

Принять фотографию из Telegram Update, выбрать максимальный `PhotoSize`, извлечь метаданные
(`file_id`, `file_unique_id`, `file_size`, `width`, `height`), сохранить их в состоянии диалога,
перевести сценарий в `WAITING_DATETIME` и запросить дату — без скачивания изображения на сервер.
Требования: US-004-01…US-004-04, AC-004-01…AC-004-09, TC-004-01…TC-004-04, IT-004-01…IT-004-03,
BR-004-01…BR-004-09, ERR-004-01…ERR-004-03 из `docs/specs/SPEC-004.md`.

## 2. Решения, принятые при планировании

Спецификация не отвечает на часть вопросов или допускает варианты. Ниже выбран вариант и причина.
Все решения можно изменить.

| № | Решение | Обоснование |
|---|---|---|
| D1 | `PhotoData` (§23) и выбор размера — `domain/photo.py`: DTO, структурный протокол `PhotoSizeLike` и функция `select_largest_photo`. Модуль не импортирует telebot | Domain не зависит от внешних библиотек (матрица SPEC-001). `telebot.types.PhotoSize` удовлетворяет протоколу структурно. §17: PhotoData — внутренний контракт |
| D2 | Максимальный размер выбирается по площади `width × height`, а не через `photo[-1]` | §10 разрешает `[-1]` для стандартного Update, но требование BR-004-04 и AC-004-03 — «максимальный доступный». Выбор по площади выполняет требование при любом порядке массива |
| D3 | `PhotoService.handle_photo(telegram_user_id, photo_sizes) -> PhotoData` в `services/photo_service.py` (§22): проверка пустого списка и `file_id`, логи §29, ошибки `PhotoProcessingError` | §21 задаёт цепочку Handler → Application Service. `telegram_user_id` нужен для логов (§29). Сервис не импортирует telebot (BR-04 SPEC-001) |
| D4 | Данные FSM — плоские ключи черновика с именами из §16: `telegram_file_id`, `telegram_file_unique_id`, `file_size`, `width`, `height`. Значения строками (хранилище состояний telebot), `file_size` не пишется, если его нет. Ключ `photo_file_id` из SPEC-003 заменён на `telegram_file_id` | §16 задаёт имена. Минимум — `telegram_file_id` (§16). Совпадает с будущими колонками `posts` (§20) |
| D5 | `DialogService.receive_photo` принимает `PhotoData` и переписывает черновик целиком; `receive_text` читает `telegram_file_id` | BR-004-05: фото доступно следующему шагу. Замена фото (BR-004-09) сводится к перезаписи черновика, как и в D5 SPEC-003 |
| D6 | Тексты: после принятия фото — точный текст §25 (включая пример `07.10.2026 15:00`); на шаге фото вместо фото — точный текст §26 «Отправь фотографию, которую нужно опубликовать.» | §6.1 и §25 задают сообщение дословно, AC-004-07 — подсказку формата. §26 задаёт ответ на неверный тип (AC-004-08) |
| D7 | Ответ при замене фото остаётся прежним («Фото заменено. …» с запросом даты) | §27 требует лишь «снова запрашивает дату» и не задаёт текст. Сохраняет поведение D5 SPEC-003 без изменений |
| D8 | ERR-004-02 (пустой массив) и ERR-004-03 (нет `file_id`): `select_largest_photo` возбуждает `PhotoProcessingError`, `PhotoService` логирует ошибку («зарегистрировать ошибку в логах»), обработчик отвечает запросом фото, FSM не меняется | ERR-004-01…ERR-004-03. «Запросить фотографию» — текст §26. Сообщение об ошибке не показывается пользователю (§30) |
| D9 | ERR-004-03 проверяется на уровне `select_largest_photo` и покрывается unit-тестами: pyTelegramBotAPI не разбирает Update без `file_id` (конструктор `PhotoSize` требует аргумент), поэтому сквозной тест на fake API невозможен | Разбор `telebot.types.PhotoSize.de_json` → `cls(**obj)`: отсутствие `file_id` падает до обработчиков |
| D10 | Логи §29: INFO «Photo received user_id=…» и «Photo selected width=… height=…» в `PhotoService.handle_photo`; бинарные данные не логируются | §29 «допускается». Проверяются юнит-тестом на caplog |
| D11 | Записи в БД при приёме фото нет (BR-004-08); поля `posts.telegram_file_id`, `posts.telegram_file_unique_id` появятся с таблицей в SPEC-008 (§20) | §19. Продолжение D9 SPEC-003: черновик живёт в FSM, а не в БД |
| D12 | Обработчик фото остаётся в `handlers/dialog.py` (регистрация `content_types=["photo"]`, только личные чаты — D14 SPEC-003). Оркестрация: `PhotoService.handle_photo` → `DialogService.receive_photo` → ответ | §24 требует обработку `content_types=["photo"]`, но не требует отдельного модуля. Аналогично `handlers/start.py`: обработчик вызывает сервисы |
| D13 | AC-004-05 (без локального файла) проверяется сквозным тестом: после шага фото на диске нет файлов изображений | Требование проверяемо только негативно: код не делает ничего с файлами |
| D14 | Код не скачивает и не хранит изображение; `file_id` не выводится пользователю (§14, §30) | BR-004-02, BR-004-03. Тексты ответов не содержат идентификаторов |
