# PostMaster

Telegram-бот для отложенных публикаций фотографий.

Реализованы фундамент проекта по [SPEC-001](docs/specs/SPEC-001.md): структура слоёв,
настройки, логирование, подключение к базе данных, Long Polling и Scheduler. Далее идут
регистрация пользователя и команда `/start` ([SPEC-002](docs/specs/SPEC-002.md)), состояния
сценария создания публикации ([SPEC-003](docs/specs/SPEC-003.md)) и приём фотографии
([SPEC-004](docs/specs/SPEC-004.md)). Остальные команды появятся в следующих спецификациях.

## Требования

- Python 3.12 или новее
- Для запуска в контейнере: Docker Engine и Docker Compose v2

## Настройка

Скопируйте шаблон и заполните токен бота, который выдаёт @BotFather:

```bash
cp .env.example .env
```

| Переменная     | Обязательна | По умолчанию                           | Назначение                                              |
|----------------|-------------|----------------------------------------|---------------------------------------------------------|
| `BOT_TOKEN`    | да          | —                                      | Токен бота. В логи и тексты ошибок не попадает          |
| `DATABASE_URL` | нет         | `sqlite+aiosqlite:///data/postmaster.db` | Строка подключения SQLAlchemy с асинхронным драйвером |
| `LOG_LEVEL`    | нет         | `INFO`                                 | `DEBUG`, `INFO`, `WARNING`, `ERROR` или `CRITICAL`      |
| `DEFAULT_TIMEZONE` | нет     | `UTC`                                  | Часовой пояс в формате IANA, например `Europe/Moscow`. Действует, пока пользователь не задал свой (SPEC-002) |

Переменные окружения имеют приоритет над файлом `.env`. Файл `.env` не попадает в Git и в образ Docker.

## Запуск локально

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
python -m postmaster
```

Команда `postmaster` после установки делает то же самое. Остановка: `Ctrl+C` или сигнал `SIGTERM`.

## Запуск в Docker

```bash
docker compose up -d --build
docker compose logs -f postmaster
docker compose down
```

База данных SQLite хранится в каталоге `./data` на хосте. Контейнер работает от пользователя
с uid 1000, поэтому этот каталог должен быть доступен ему на запись:

```bash
mkdir -p data && sudo chown -R 1000:1000 data
```

## Команды бота

| Команда  | Что делает |
|----------|------------|
| `/start` | Регистрирует пользователя при первом вызове и не создаёт дубликат при повторном. Если имя или username изменились, обновляет их. Отвечает приветствием и ждёт фотографию (SPEC-002). Начинает новый сценарий из любого шага (SPEC-003). При ошибке регистрации просит повторить позже |

Сценарий создания публикации идёт по шагам (SPEC-003, SPEC-004):

1. `/start` — бот ждёт фотографию.
2. Фотография — бот сохраняет метаданные изображения (`file_id` и связанные поля) и просит
   дату и время публикации в формате `ДД.ММ.ГГГГ ЧЧ:ММ`, например `07.10.2026 15:00`.
   Само изображение не скачивается на сервер: при публикации используется Telegram `file_id`.
   Новая фотография на этом шаге заменяет предыдущую, и бот снова просит дату.
3. Дата — время считается в часовом поясе пользователя (`DEFAULT_TIMEZONE`, пока пользователь не задал свой). Дата должна быть в будущем. Бот подтверждает создание публикации и возвращает сценарий в исходное состояние.

Сообщения, которые не подходят текущему шагу, не меняют состояние. Бот присылает подсказку о том, что он ждёт.

Сценарий работает только в личных чатах. В группах бот не отвечает.

Состояние сценария хранится в памяти процесса. После перезапуска бота нужно снова отправить `/start`.
Публикация пока не сохраняется в базе данных: таблица `posts` появится в SPEC-008.

## Коды завершения

| Код | Значение                                                                 |
|-----|--------------------------------------------------------------------------|
| 0   | Штатная остановка по `SIGINT` или `SIGTERM`                              |
| 1   | Ошибка запуска или работы: токен отклонён, нет связи с Telegram, БД недоступна |
| 2   | Ошибка конфигурации: не задан или некорректен `BOT_TOKEN`, неверный `LOG_LEVEL` или `DEFAULT_TIMEZONE` |

## Архитектура

Код находится в `src/postmaster/`. Каждый слой — отдельный подпакет:

| Слой           | Назначение                                                        |
|----------------|-------------------------------------------------------------------|
| `bot`          | Клиент Telegram, транспорт обновлений (Long Polling), хранилище состояния диалога |
| `handlers`     | Telegram-обработчики. Только разбор сообщения и вызов сервиса     |
| `services`     | Бизнес-логика: `DialogService`, `UserService`, `PhotoService`, `PostService`, `PublicationService`, `SchedulerService` |
| `publishers`   | Интерфейс `Publisher` и реализации публикации                     |
| `repositories` | Доступ к данным. Единственное место с запросами к БД              |
| `domain`       | Доменные модели без зависимостей от Telegram и БД                 |
| `database`     | Движок SQLAlchemy, сессии, базовый класс моделей                  |
| `utils`        | Вспомогательные функции, в том числе логирование и маскировка     |

Корневые модули: `config.py` (настройки), `app.py` (точка входа и жизненный цикл),
`__main__.py` (запуск через `python -m postmaster`).

Правила, которые проверяет тест `tests/test_architecture.py`:

- логика не находится в обработчиках Telegram;
- данные читаются и пишутся только через репозитории;
- публикация выполняется только через `Publisher`;
- сервисы, включая `SchedulerService`, не импортируют `telebot`: задания Scheduler вызывают прикладные сервисы, а не Telegram API;
- в MVP используется Long Polling;
- циклических зависимостей между модулями и слоями нет.

## Переход на Webhook

Получение обновлений описано протоколом `Transport` (`src/postmaster/bot/transport.py`) с методами
`run()` и `stop()`. Сейчас есть одна реализация, `PollingTransport`. Для Webhook нужно добавить
новую реализацию протокола и выбрать её в `Application.from_settings`. Обработчики, сервисы и
репозитории при этом не меняются.

## Тесты и проверки

```bash
pytest
ruff check .
ruff format --check .
```

Тесты не обращаются к api.telegram.org. Long Polling проверяется на локальном fake-сервере
Telegram Bot API (`tests/fake_telegram.py`). Сквозной запуск в подпроцессе проверяет коды
завершения и отсутствие токена в выводе.
