# PostMaster

Telegram-бот для отложенных публикаций фотографий.

Реализованы фундамент проекта по [SPEC-001](docs/specs/SPEC-001.md): структура слоёв,
настройки, логирование, подключение к базе данных, Long Polling и Scheduler. Далее идут
регистрация пользователя и команда `/start` ([SPEC-002](docs/specs/SPEC-002.md)), состояния
сценария создания публикации ([SPEC-003](docs/specs/SPEC-003.md)) и приём фотографии
([SPEC-004](docs/specs/SPEC-004.md)), строгая валидация даты и времени
([SPEC-005](docs/specs/SPEC-005.md)) и преобразование часовых зон
([SPEC-006](docs/specs/SPEC-006.md)) и модель пользователей
([SPEC-007](docs/specs/SPEC-007.md)), а также таблица и репозиторий публикаций
(SPEC-008), их сохранение из диалога с регистрацией задания (SPEC-009), защита
от двойной публикации через atomic claim ([SPEC-013](docs/specs/SPEC-013.md)),
отправка напоминания владельцу поста ([SPEC-014](docs/specs/SPEC-014.md)),
автопубликация в Telegram-канал ([SPEC-015](docs/specs/SPEC-015.md)) и единая
абстракция `Publisher` с `PublisherResolver` ([SPEC-016](docs/specs/SPEC-016.md)).
Остальные команды появятся в следующих спецификациях.

## Требования

- Python 3.12 или новее
- Для запуска в контейнере: Docker Engine и Docker Compose v2

## Настройка

Скопируйте шаблон и заполните токен бота, который выдаёт @BotFather:

```bash
cp .env.example .env
```

| Переменная     | Обязательна | По умолчанию                           | Назначение                                              |
|----------------|-------------|----------------------------------------|---------------------------------------------------------|
| `BOT_TOKEN`    | да          | —                                      | Токен бота. В логи и тексты ошибок не попадает          |
| `DATABASE_URL` | нет         | `sqlite+aiosqlite:///data/postmaster.db` | Строка подключения SQLAlchemy с асинхронным драйвером |
| `LOG_LEVEL`    | нет         | `INFO`                                 | `DEBUG`, `INFO`, `WARNING`, `ERROR` или `CRITICAL`      |
| `DEFAULT_TIMEZONE` | нет     | `Europe/Moscow`                                  | Часовой пояс в формате IANA, например `Europe/Moscow`. Действует, пока пользователь не задал свой (SPEC-002) |
| `DEFAULT_POST_MODE` | нет | `REMINDER` | Резервный режим (`REMINDER` или `TELEGRAM`); старый `POST_MODE` поддерживается как alias. Выбор пользователя обязателен для каждого нового поста. |
| `TELEGRAM_TARGET_ALLOWLIST` | нет | — | CSV разрешённых каналов, например `@channel_one,-1001234567890`. Пустой список не ограничивает выбор. |
| `HEALTH_FILE` | нет | `data/health.json` | Путь к JSON-отчёту health check (SPEC-029) |
| `HEALTH_MAX_AGE_SECONDS` | нет | `90` | Максимальный возраст отчёта, после которого он считается устаревшим |
| `BACKUP_PATH` | нет | `data/backup.db` | Путь к файлу резервной копии SQLite (SPEC-030) |

Переменные окружения имеют приоритет над файлом `.env`. Файл `.env` не попадает в Git и в образ Docker.

## Запуск локально

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
python -m postmaster
```

Команда `postmaster` после установки делает то же самое. Остановка: `Ctrl+C` или сигнал `SIGTERM`.

## Запуск в Docker

```bash
docker compose up -d --build
docker compose logs -f postmaster
docker compose down
```

База данных SQLite хранится в каталоге `./data` на хосте. Контейнер работает от пользователя
с uid 1000, поэтому этот каталог должен быть доступен ему на запись:

```bash
mkdir -p data && sudo chown -R 1000:1000 data
```

В `docker-compose.yml` настроен `HEALTHCHECK` (SPEC-029): каждые 30 секунд выполняется
`python -m postmaster health`, который читает JSON-отчёт из `data/health.json`,
написанный работающим приложением. Docker помечает контейнер `unhealthy`, если
приложение зависло, БД недоступна или Scheduler остановлен.

## Команды бота

| Команда  | Что делает |
|----------|------------|
| `/start` | Регистрирует пользователя при первом вызове и не создаёт дубликат при повторном. Если имя или username изменились, обновляет их. Отвечает приветствием и ждёт фотографию (SPEC-002). Начинает новый сценарий из любого шага (SPEC-003). При ошибке регистрации просит повторить позже |

Имя и username могут отсутствовать в Telegram: `/start` всё равно создаёт пользователя
по `telegram_user_id` и не показывает «None» в приветствии. В БД для нового пользователя
`timezone=NULL`; при работе со временем применяется конфигурационный пояс.

Сценарий создания публикации идёт по шагам (SPEC-003…009):

1. `/start` — бот ждёт фотографию.
2. Отправьте фотографию (можно с подписью). Бот сохраняет её `file_id`, не скачивая файл,
   и предлагает выбрать «🔔 Напомнить мне» или «📢 Опубликовать в Telegram».
3. Для Telegram укажите `@channel_name` или числовой ID канала. Если настроен
   `TELEGRAM_TARGET_ALLOWLIST`, канал должен входить в список. Бот должен иметь право
   публикации; Telegram проверяет это при отправке.
4. Укажите дату и время в формате `ДД.ММ.ГГГГ ЧЧ:ММ` в часовом поясе пользователя.
   Время должно быть в будущем. При ошибке бот сохраняет черновик и ждёт корректную дату.
   Новая фотография в процессе заменяет предыдущую, сохраняя выбранный режим и канал.

Сообщения, которые не подходят текущему шагу, не меняют состояние. Бот присылает подсказку о том, что он ждёт.

Сценарий работает только в личных чатах. В группах бот не отвечает.

Состояние черновика хранится в памяти процесса. После перезапуска для незавершённого
сценария нужно снова отправить `/start`. Готовые публикации сохраняются в SQLite (`posts`)
и не теряются: `PostService` создаёт `PENDING`, получает внутренний `users.id`, коммитит запись
и только потом ставит задание Scheduler по `post_id` и UTC-времени. При ошибке БД фото остаётся
в черновике для повторного ввода даты; при ошибке Scheduler запись остаётся `PENDING`, бот
показывает предупреждение и очищает черновик, чтобы повтор не создавал дубликат. После успеха
новая фотография начинает новый сценарий без старых данных. Режим и канал хранятся
в записи каждого поста; изменение настроек не меняет ранее созданные публикации.
`DEFAULT_POST_MODE` (или прежний `POST_MODE`, если новый параметр не задан) сохраняется
для совместимости конфигурации, но не заменяет обязательный выбор в диалоге.
Старый `TELEGRAM_TARGET_ID` не подставляется вместо канала пользователя.

При старте ожидающие задания восстанавливаются из базы; для выполнения выбирается Publisher
по сохранённому типу поста. Подтверждение планирования не означает факт доставки.

Старые SQLite-БД, созданные до SPEC-007, всё ещё могут иметь `users.first_name NOT NULL`:
`create_all` не изменяет существующие таблицы. Для обновления этой колонки потребуется
миграция SPEC-027. До неё регистрация с отсутствующим именем работает лишь на новых БД.

## Коды завершения

| Код | Значение                                                                 |
|-----|--------------------------------------------------------------------------|
| 0   | Штатная остановка по `SIGINT` или `SIGTERM`. Для `python -m postmaster health` — отчёт healthy |
| 1   | Ошибка запуска или работы: токен отклонён, нет связи с Telegram, БД недоступна. Для `python -m postmaster health` — отчёт unhealthy, устарел, повреждён или отсутствует |
| 2   | Ошибка конфигурации: неверный `BOT_TOKEN`, `LOG_LEVEL`, `DEFAULT_TIMEZONE`, `DEFAULT_POST_MODE` или `TELEGRAM_TARGET_ALLOWLIST` |

## Управление публикациями (SPEC-017, PM-04)

### Команда `/my_posts`

Возвращает до 20 собственных `PENDING`-публикаций. Для каждой публикации
выводится отдельное сообщение с блоком деталей и двумя inline-кнопками:

- `❌ Отменить` — атомарно переводит пост в `CANCELLED` и удаляет задачу
  Scheduler через `CancelService` (проверка владельца и `PENDING` на сервисном
  уровне);
- `🕒 Перенести` — переключает FSM в режим ввода новой даты/времени
  (`ДД.ММ.ГГГГ ЧЧ:ММ`); после валидации формата и «в будущем» относительно
  timezone пользователя `RescheduleService` обновляет `scheduled_at_utc`
  атомарным conditional UPDATE и пересоздаёт задачу Scheduler. Тип публикации,
  фото, подпись и target-канал остаются неизменными.

Если у пользователя больше 20 публикаций, выводятся первые 20 и предупреждение;
если публикаций нет — сообщение `У тебя пока нет запланированных публикаций.`

Подмена callback data (например `cancel:<id_чужого_поста>`) блокируется
повторной проверкой владельца и статуса в сервисном слое.

### Согласованность БД и Scheduler

БД остаётся источником истины. При ошибке обновления Scheduler после
изменения в БД Recovery перерегистрирует задачу по актуальному
`scheduled_at_utc` при следующем старте приложения.

## Health check (SPEC-029)

```bash
python -m postmaster health
# код 0 → healthy
# код 1 → unhealthy / отчёт устарел / повреждён / отсутствует
# код 2 → ошибка конфигурации

# С флагами:
python -m postmaster health --print           # печатает JSON-отчёт
python -m postmaster health --health-file path/to/report.json
python -m postmaster health --max-age-seconds 60
```

Проверяет три индикатора: ``process`` (всегда ok в живом процессе),
``database`` (``SELECT 1`` через SQLAlchemy), ``scheduler``
(``SchedulerService.running``). Отчёт атомарно пишется в `HEALTH_FILE`
каждые 30 секунд; не содержит секретов, паролей БД и пользовательских
данных.

## Резервное копирование SQLite (SPEC-030)

```bash
python -m postmaster backup
# код 0 → backup создан и проверен
# код 1 → ошибка backup
# код 2 → ошибка конфигурации

# С флагами:
python -m postmaster backup --source /path/to/db.sqlite
python -m postmaster backup --destination /var/backups/postmaster.db
```

Создаёт резервную копию SQLite через Online Backup API и проверяет её
целостность (`PRAGMA integrity_check`). Активная БД не меняется,
`.env` не включается (это файл SQLite, секреты хранятся отдельно).
Поддерживается только для `DATABASE_URL` с SQLite.

## Архитектура

Код находится в `src/postmaster/`. Каждый слой — отдельный подпакет:

| Слой           | Назначение                                                        |
|----------------|-------------------------------------------------------------------|
| `bot`          | Клиент Telegram, транспорт обновлений (Long Polling), хранилище состояния диалога |
| `handlers`     | Telegram-обработчики. Только разбор сообщения и вызов сервиса     |
| `services`     | Бизнес-логика: `DialogService`, `UserService`, `PhotoService`, `PostService`, `PublicationService`, `SchedulerService` |
| `publishers`   | Интерфейс `Publisher`, `PublishResult`, `PublisherResolver` (SPEC-016), `TelegramClient` и реализации `ReminderPublisher` (SPEC-014), `TelegramPublisher` (SPEC-015) |
| `repositories` | Доступ к данным. Единственное место с запросами к БД              |
| `domain`       | Доменные модели без зависимостей от Telegram и БД                 |
| `database`     | Движок SQLAlchemy, сессии, базовый класс моделей                  |
| `utils`        | Вспомогательные функции, в том числе логирование и маскировка     |

Корневые модули: `config.py` (настройки), `app.py` (точка входа и жизненный цикл),
`__main__.py` (запуск через `python -m postmaster`).

Правила, которые проверяет тест `tests/test_architecture.py`:

- логика не находится в обработчиках Telegram;
- данные читаются и пишутся только через репозитории;
- публикация выполняется только через `Publisher`;
- сервисы, включая `SchedulerService`, не импортируют `telebot`: задания Scheduler вызывают прикладные сервисы, а не Telegram API;
- в MVP используется Long Polling;
- циклических зависимостей между модулями и слоями нет.

## Переход на Webhook

Получение обновлений описано протоколом `Transport` (`src/postmaster/bot/transport.py`) с методами
`run()` и `stop()`. Сейчас есть одна реализация, `PollingTransport`. Для Webhook нужно добавить
новую реализацию протокола и выбрать её в `Application.from_settings`. Обработчики, сервисы и
репозитории при этом не меняются.
